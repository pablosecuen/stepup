### Ejecución real de pgTAP sin Docker (Fase 10)

Este entorno de trabajo nunca tuvo Docker Desktop instalado, así que `supabase test db` (que lo requiere) nunca fue una opción. En Fase 10 se encontró que el proyecto real SÍ tiene la extensión `pgtap` disponible (`pg_available_extensions`, versión `1.3.3`, `installed_version: null` — disponible pero no habilitada) y que el rol usado por `supabase db query --linked` (`postgres`, real pero no superusuario) puede instalarla y usarla. `CREATE EXTENSION` es DDL transaccional en Postgres, así que se ejecutaron los 3 archivos reales contra el proyecto real dentro de una transacción descartable:

```sql
begin;
create extension if not exists pgtap with schema extensions;
set local search_path to public, auth, extensions, pg_catalog;
-- (contenido real del archivo de prueba trackeado, sin su propio BEGIN/ROLLBACK exterior)
rollback;
```

Verificado antes de aceptar el resultado como válido: una prueba mínima (`plan(1)`/`ok(true, ...)`/`finish()`) confirmó que `plan/ok/finish` funcionan dentro de esa transacción, y que tras el `ROLLBACK` la extensión vuelve a `installed_version: null` — confirmado de nuevo después de cada uno de los 3 archivos reales. Los archivos trackeados nunca se modificaron para esto — se generaron copias temporales fuera del repositorio (`scratchpad`, nunca commiteadas), con una única instrumentación añadida (una tabla temporal `__tap_capture__` que graba cada línea TAP para poder leerla completa, porque la herramienta de consulta usada sólo muestra el resultado del último `SELECT` de un archivo) — la lógica, el orden, los roles y los datos de cada aserción quedaron exactamente iguales a los archivos trackeados.

### Regresión investigada — `start_date` de series, cierre (ronda dedicada, sin cambios de fase)

**Pedido:** investigar y corregir el "hallazgo menor" de la ronda anterior ("la fecha seleccionada al crear una serie se guarda un día antes"), revisando toda la cadena (input HTML, Server Action, conversión fecha↔Date↔texto, repositorio, RPC/columna de Postgres, lectura/renderizado), sin agregar compensaciones de huso horario.

**Resultado de la investigación: NO es un bug — el reporte anterior fue una interpretación errónea de mi parte, corregida acá con evidencia real, no simplemente descartada.** Cadena completa revisada:
- `new-lesson-form.tsx`: el `<input type="date">` entrega siempre un string `YYYY-MM-DD` (sin componente horario) — nunca se construye un `Date` de JS en el cliente.
- `lib/actions/calendar.ts` (`createRecurrenceSeriesAction`): normaliza ese string al **lunes de esa semana** antes de guardar. Esto es una invariante REAL y obligatoria del motor de recurrencia (`assertRecurrenceRule` en `recurrence-engine.ts` línea 29-31 **lanza una excepción** si `startDate` no es lunes), no una decisión arbitraria de esta sesión — ya estaba así desde Fase 3, con tests desde entonces (`getDateKeyJsDay("2026-09-14")` ya testeado como lunes en `timezone.test.ts`).
- El cálculo del lunes (`addDaysToDateKey`/`getDateKeyJsDay`) usa exclusivamente `Date.UTC`/`getUTCDate`/`getUTCDay` sobre los componentes año/mes/día — nunca `.getDate()`/`.getDay()` ni la zona horaria del proceso Node, así que es 100% estable sin importar dónde corra el servidor.
- `recurrence_rules.start_date` es columna Postgres `date` (nunca `timestamptz`) — no hay conversión de zona horaria posible en el tramo repositorio→RPC→columna→lectura; el string se pasa idéntico en todo el camino (`recurrenceSeriesInputToPayload`).
- Clase única, "Editar futuras" (`splitRecurrenceThisAndFuture`/`planRecurrenceSplit`) y "Modificar participantes" (`changeRecurrenceParticipantsFromDate`) revisados también — todos usan el mismo patrón correcto (`localDateTimeToInstantIso`/`getLocalDateKey` con `Intl.DateTimeFormat` real para instantes; aritmética UTC pura de componentes para fechas civiles). Ningún punto de la cadena interpreta un `YYYY-MM-DD` pasando por UTC de forma incorrecta.
- **Lo que realmente le importa a la profesora — en qué día cae la primera clase — nunca se ve afectado:** `generateOccurrences` arranca a buscar sesiones reales desde `startDate` (el lunes ancla) en adelante, así que la primera ocurrencia REAL sigue siendo exactamente la fecha civil que ella eligió (o una posterior, según el patrón). `start_date` de la regla nunca se muestra en ninguna pantalla — sólo se usa como ancla técnica interna.

### Errores de red, idempotencia de Calendario y correcciones de Respaldo (bloque previo a staging, aplicado y verificado)

El E2E de red del bloque anterior destapó un bloqueo estructural y tres hallazgos funcionales; todo quedó corregido, **aplicado** (migraciones 35 y 36) y reverificado contra el esquema real. 36/36 migraciones local=remote.

**1. Errores de red en Server Actions (bloqueo de lanzamiento, ya corregido).** Probado en build de producción interceptando sólo requests con `Next-Action`: `useActionState`/`startTransition(async)` terminaban en `app/error.tsx` (desmonta el formulario, pierde todo lo escrito) y un `await` directo en un handler no lo captura nadie (rechazo silencioso; los `setBusy(false)` nunca corrían y el botón quedaba bloqueado). Corrección mínima y central: `lib/actions/network-guard.ts` (`guardNetwork`, `guardFormAction`, `restoreFormValues`) + `lib/actions/use-guarded-action-state.ts` (reemplazo directo de `useActionState`) + `app/error.tsx` como última defensa. La falla de red se convierte en el mismo `{ error }` que ya muestra cada pantalla ("No se pudo conectar con el servidor. Revisá tu conexión y volvé a intentar…"), repone lo escrito en formularios no controlados (React 19 los resetea aun con un `{ error }` devuelto) y nunca simula éxito. Aplicado a 11 formularios y 37 llamadas imperativas; una guarda estructural (`network-guard-coverage.test.ts`) impide agregar una llamada a un Server Action sin protección (ya encontró una real, un `.then` sin `await` en `import-history.tsx`). Limitación documentada: los formularios envueltos pierden el envío antes de hidratar (progressive enhancement) — aceptable, todos requieren JS.

**2. Idempotencia de creación de clase única y serie (migración `20261001150000_calendar_creation_idempotency.sql`).** Causa raíz: `create_calendar_lesson`/`create_recurrence_series` no tenían clave de idempotencia; tras una respuesta perdida el reintento de una serie creaba una **segunda regla** y el de una clase única sólo no duplicaba porque la acción lo rechazaba con "se superpone". Diseño (mismo patrón que pagos/registro): `operation_id uuid` + UNIQUE parcial `(owner_id, operation_id)` en `calendar_lessons` y `recurrence_rules`; ambas RPC lo exigen (`22023`), hacen `INSERT … ON CONFLICT … DO NOTHING RETURNING` y devuelven la fila canónica sin tocar roster ni `updated_at`; una sola transacción (rollback completo). El cliente genera el UUID una vez por borrador (`useDraftOperationId`, sessionStorage), sobrevive recarga/falla/respuesta perdida; las acciones ya no hacen `redirect()` y devuelven `createdOperationId` para que el formulario rote la clave **sólo** tras la confirmación del servidor. Verificado: 46 pgTAP nuevos, concurrencia real de dos conexiones (la segunda espera ~3 s en el índice único y devuelve el mismo id), y E2E real con la cuenta QA — clase y serie con respuesta perdida + reintento (misma fila/regla, `updated_at` intacto, éxito canónico), recarga, pestaña duplicada (misma clave, 1 sola fila) y pestañas independientes (claves distintas), `operation_id` nuevo crea otra operación y el solapamiento sigue rechazándose. Observación de diseño (no es un bug): una pestaña que quedó con una clave ya usada por otra pestaña duplicada devuelve la clase canónica en vez de crear una nueva con datos distintos — es el costo de compartir la clave entre pestañas duplicadas.

**3. Falso conflicto en toda creación de serie (corregido).** `loadCalendarViewForRange` incluye las ocurrencias de TODAS las reglas, también de la recién creada, y el chequeo posterior a crearla no las excluía: la serie chocaba consigo misma y toda creación terminaba en "Serie creada, pero hay un conflicto real". `lib/calendar/conflict-candidates.ts` (`toConflictCandidates`, 8 pruebas) excluye únicamente la propia serie; verificado en vivo que un horario libre navega sin aviso y que un choque real con otra serie se sigue detectando.

**4. Respaldo: singletons opcionales con JSON null + undo idempotente (migración `20261001160000_backup_import_null_singletons_and_undo_idempotency.sql`).** Causa raíz: `validateBackupPayload` normaliza una colección ausente con `?? null`, y en Postgres `payload->'clave'` sobre un JSON `null` es el escalar `'null'::jsonb`, no SQL NULL; `_classify_singleton` (guarda `is null`) la trataba como presente ("se creará") y `_apply_singleton` insertaba `NULL` en `budget_distribution_settings` (`23502`), revirtiendo TODA la importación. El móvil (`buildBackupV2.ts`) **siempre** emite estas claves, con `null` si nunca se configuraron — es el caso común. ### B10 — Asistente de importación en lenguaje simple (6/oct/2026) — implementado

**Definición.** Bloque posterior a B9: simplifica los textos y la estructura del asistente de importación (Configuración → Respaldo) para una persona no técnica. NO cambia la lógica de importar, validar, deshacer, la idempotencia, el rollback, las RPC, la base de datos ni el formato del respaldo: las mismas Server Actions reciben los mismos argumentos.

**Flujo anterior.** Un botón «Analizar último respaldo» y, al terminar, una pantalla única con una sección por tabla: «N nuevo(s), N en conflicto…», nombres de columnas como «birth_date» y valores en JSON, ids de la app móvil en `font-mono`, «componente(s)», «fila(s)», «Agregados omitidos por referencia rota», «Colecciones fuera de esta versión» con los motivos técnicos de la base («RLS sólo SELECT»), conflictos de alumnos sin decir de qué alumno, «vincular» / «Omitir por ahora», errores de las RPC mostrados tal cual (con ids y «preview»), «Ya revisé los resultados, no necesito poder deshacer esto» que quitaba la opción de deshacer sin confirmar y, tras descartar, la pantalla volvía a ofrecer deshacer.

**Flujo nuevo.** Tres pasos con indicador (Analizar → Revisar y decidir → Resultado) y el foco en el título de cada uno.
1. *Analizar:* «Qué va a pasar» — no se elige ningún archivo (es la última copia que subió la app móvil), analizar no cambia nada, el usuario decide, y deshacer tiene límites.
2. *Revisar y decidir:* fecha de la copia, vigencia de la revisión (30 min, con la hora), vocabulario fijo (agregar, conservar, reemplazar, no importar, deshacer), una tarjeta por tema, cada dato reemplazable como casilla «Reemplazar «Teléfono»» con «En la web: … → En la copia: …» (sin marcar = se conserva), el nombre del alumno en cada conflicto (lectura adicional de nombres con el mismo helper de los duplicados), duplicados con tres opciones que dicen qué hacen (la segura, «No importar», es la de por defecto) y «Antes de confirmar» con el resumen en frases y la confirmación reforzada de siempre («IMPORTAR»).
3. *Resultado:* qué se agregó con los nombres humanos, aviso si fue una repetición (`replayed`, antes no se mostraba), cómo deshacer y cómo quitar la opción de deshacer (ahora con confirmación que dice la consecuencia).

**Terminología reemplazada.** fila(s)/registro(s) → elementos; componente(s) → grupos de cobros (con su contenido por tipo: «2 pagos, 1 cobro»); «agregados omitidos por referencia rota» → «no se importarán» con el motivo en una frase; checksum/versión de esquema/nombres de tabla/columnas/ids → nunca se muestran; backup → copia de seguridad; preview → revisión; «Se recuperará» → «Se agregará»; «vincular» → «unirlos»; «Previsualizar deshacer» → «Revisar si se puede deshacer»; «Confirmar importación» → «Confirmar e importar»; «Cancelar — no se importarán datos» → «Cancelar (no se importa nada)». Los motivos técnicos de lo excluido se reemplazan por «Todavía no se puede importar a la web.».

**Errores.** `lib/backup/import-copy.ts` (puro) traduce cada mensaje de las RPC y de la validación a una frase con «qué pasó con tus datos» y un código de soporte estable (`review_expired`, `review_outdated`, `integrity_check_failed`, `undo_blocked`, `backup_too_large`, `network_unreachable`…; sin datos, ids ni tablas). Lo desconocido cae en una frase genérica del paso donde ocurrió. Dos cuidados: un error inesperado o una red cortada al importar NO afirma que no se importó nada (manda al historial y recuerda que reintentar no duplica, porque reconfirmar la misma revisión devuelve el resultado ya aplicado), y la validación se traduce por su código, nunca por su texto ni por el nombre de la colección.
