### Ejecución real de pgTAP sin Docker (Fase 10)

Este entorno de trabajo nunca tuvo Docker Desktop instalado, así que `supabase test db` (que lo requiere) nunca fue una opción. En Fase 10 se encontró que el proyecto real SÍ tiene la extensión `pgtap` disponible (`pg_available_extensions`, versión `1.3.3`, `installed_version: null` — disponible pero no habilitada) y que el rol usado por `supabase db query --linked` (`postgres`, real pero no superusuario) puede instalarla y usarla. `CREATE EXTENSION` es DDL transaccional en Postgres, así que se ejecutaron los 3 archivos reales contra el proyecto real dentro de una transacción descartable:

```sql
begin;
create extension if not exists pgtap with schema extensions;
set local search_path to public, auth, extensions, pg_catalog;
-- (contenido real del archivo de prueba trackeado, sin su propio BEGIN/ROLLBACK exterior)
rollback;
```

Verificado antes de aceptar el resultado como válido: una prueba mínima (`plan(1)`/`ok(true, ...)`/`finish()`) confirmó que `plan/ok/finish` funcionan dentro de esa transacción, y que tras el `ROLLBACK` la extensión vuelve a `installed_version: null` — confirmado de nuevo después de cada uno de los 3 archivos reales. Los archivos trackeados nunca se modificaron para esto — se generaron copias temporales fuera del repositorio (`scratchpad`, nunca commiteadas), con una única instrumentación añadida (una tabla temporal `__tap_capture__` que graba cada línea TAP para poder leerla completa, porque la herramienta de consulta usada sólo muestra el resultado del último `SELECT` de un archivo) — la lógica, el orden, los roles y los datos de cada aserción quedaron exactamente iguales a los archivos trackeados.

### Regresión investigada — `start_date` de series, cierre (ronda dedicada, sin cambios de fase)

**Pedido:** investigar y corregir el "hallazgo menor" de la ronda anterior ("la fecha seleccionada al crear una serie se guarda un día antes"), revisando toda la cadena (input HTML, Server Action, conversión fecha↔Date↔texto, repositorio, RPC/columna de Postgres, lectura/renderizado), sin agregar compensaciones de huso horario.

**Resultado de la investigación: NO es un bug — el reporte anterior fue una interpretación errónea de mi parte, corregida acá con evidencia real, no simplemente descartada.** Cadena completa revisada:
- `new-lesson-form.tsx`: el `<input type="date">` entrega siempre un string `YYYY-MM-DD` (sin componente horario) — nunca se construye un `Date` de JS en el cliente.
- `lib/actions/calendar.ts` (`createRecurrenceSeriesAction`): normaliza ese string al **lunes de esa semana** antes de guardar. Esto es una invariante REAL y obligatoria del motor de recurrencia (`assertRecurrenceRule` en `recurrence-engine.ts` línea 29-31 **lanza una excepción** si `startDate` no es lunes), no una decisión arbitraria de esta sesión — ya estaba así desde Fase 3, con tests desde entonces (`getDateKeyJsDay("2026-09-14")` ya testeado como lunes en `timezone.test.ts`).
- El cálculo del lunes (`addDaysToDateKey`/`getDateKeyJsDay`) usa exclusivamente `Date.UTC`/`getUTCDate`/`getUTCDay` sobre los componentes año/mes/día — nunca `.getDate()`/`.getDay()` ni la zona horaria del proceso Node, así que es 100% estable sin importar dónde corra el servidor.
- `recurrence_rules.start_date` es columna Postgres `date` (nunca `timestamptz`) — no hay conversión de zona horaria posible en el tramo repositorio→RPC→columna→lectura; el string se pasa idéntico en todo el camino (`recurrenceSeriesInputToPayload`).
- Clase única, "Editar futuras" (`splitRecurrenceThisAndFuture`/`planRecurrenceSplit`) y "Modificar participantes" (`changeRecurrenceParticipantsFromDate`) revisados también — todos usan el mismo patrón correcto (`localDateTimeToInstantIso`/`getLocalDateKey` con `Intl.DateTimeFormat` real para instantes; aritmética UTC pura de componentes para fechas civiles). Ningún punto de la cadena interpreta un `YYYY-MM-DD` pasando por UTC de forma incorrecta.
- **Lo que realmente le importa a la profesora — en qué día cae la primera clase — nunca se ve afectado:** `generateOccurrences` arranca a buscar sesiones reales desde `startDate` (el lunes ancla) en adelante, así que la primera ocurrencia REAL sigue siendo exactamente la fecha civil que ella eligió (o una posterior, según el patrón). `start_date` de la regla nunca se muestra en ninguna pantalla — sólo se usa como ancla técnica interna.
