# Cobros y estadísticas — causas confirmadas (11/11/2026)

## 1. «cannot delete from scalar» al modificar la cuota mensual

**Causa (reproducida en Postgres real con `supabase/tests/postgres/student_plan_json_null.cjs --before`).** 13 alumnos de la base real tienen `students.billing_plan = jsonb 'null'` (el JSON null del traslado desde la app; no es el NULL de SQL): 9 mensuales activos, 1 mensual inactivo y 3 por clase. `change_student_monthly_amount` resolvía el plan con `coalesce(billing_plan, plan derivado)`: el JSON null no es NULL de SQL, así que el plan quedaba como el escalar `null`. Luego `v_plan->>'type' <> 'monthly'` da NULL (no lanza) y `v_plan - 'pendingAmount'` falla con «cannot delete from scalar». No era visual: el error sale de la base al guardar. Ni «este mes» ni «próximo mes» (el `||` del próximo mes sobre un escalar arma un arreglo) podían funcionar para esos alumnos.

**Corrección (migración nueva `20261111100000_student_plan_json_null.sql`, PREPARADA, NO APLICADA).** Una función `effective_student_billing_plan(plan, tipo, precio)`: objeto = el plan; NULL de SQL o JSON null = «sin plan» (se deriva del tipo de cobro y el precio, igual que la web); cualquier otro valor se rechaza con un mensaje claro. Se usa en las cuatro funciones publicadas que tenían el mismo `coalesce`: `change_student_monthly_amount`, `set_student_billing_plan`, `_apply_first_month_situation` (con un JSON null, «comienza el mes próximo» podía escribir un arreglo en vez de un objeto) y `reactivate_student_with_billing`. No se edita ninguna migración histórica, no se toca ninguna fila existente (el plan derivado sólo se escribe cuando el usuario guarda un cambio, y ese cambio ya escribe un objeto completo) y no hay normalización masiva. Pendiente aparte (no tocado): `apply_financial_reconciliation` y la importación (`r6`) conservan el patrón del JSON null; la importación sigue pudiendo crearlos.

Prueba: 23 comprobaciones en Postgres real (este mes/próximo mes, cargo pendiente, pago parcial, mes saldado, centavos exactos, otra cuenta, por clase, escalar no reconocido, NULL de SQL, plan objeto) + las suites existentes `billing_plans_amounts` (60/60) y `student_initial_month` (53/53).

## 2. «Editar cuota» abría la lista de Series

`conceptItems` mandaba a `href: "/calendario/series"` para cualquier entrenamiento. Ahora cada concepto de entrenamiento conoce su acuerdo (`trainingFeeContext`, derivado de la clave `training:<acuerdo>` de sus cobros) y «Editar cuota» abre en la misma pantalla el diálogo EXISTENTE de la cuota de ESE acuerdo (alumno y entrenamiento en el título, cuota actual y cambio ya programado). Guardar o cancelar cierra el diálogo: la pestaña, la búsqueda, los filtros, el orden y la posición no se mueven porque no hay navegación. El plan de clases individuales sigue yendo a «Editar plan»; un entrenamiento sin acuerdo vinculado no ofrece cuota.

## 4. Estadísticas

**«0 h enseñadas este mes» — causa confirmada.** Consulta de solo lectura: en noviembre hay 34 clases dictadas en la cuenta principal; las 34 tienen `actual_started_at` y `actual_ended_at` pero `actual_duration_minutes` es NULL (y 0 con programada completa). Octubre: 56 de 135 en las mismas condiciones. El registro de la web guarda inicio y fin reales; `actual_duration_minutes` sólo lo escriben los traslados y «corregir sesión». Inicio sumaba sólo esa columna (`null` → 0). Ahora usa `resolveClassMinutes` (la misma resolución del reporte del alumno): duración real guardada → inicio y fin reales → programada → sin dato. Una clase grupal/entrenamiento cuenta UNA vez (es una fila de registro, no una por participante); una reprogramada no cuenta (su registro no «cuenta como clase») y la clase nueva se cuenta una vez; el mes es el civil de Argentina. Si hay clases dictadas pero ninguna con duración, el indicador dice «Sin datos» y nunca 0.

**«Alumnos que pagaron este mes» / «con deuda».** El cálculo (`buildMonthSnapshot`) es correcto: contrastado con una consulta independiente sobre la base real (cuenta principal: 20 pagaron y 6 con deuda; segunda cuenta: 0 pagaron y 4 con deuda; coinciden con la regla). Los ceros del video NO vienen del cálculo. EVIDENCIA PARA CODEX (no se modificó el contador): `components/ui/animated-number.tsx` pinta `0` (`output.textContent = formats[kind](0)`) y sólo avanza cuando el `IntersectionObserver` (umbral 0,5, `rootMargin: "-64px 0px -12% 0px"`) detecta el número. Reproducido en laboratorio a 375, 390, 430 y 1366 px: un `AnimatedNumber value={7}` ubicado en el 12 % inferior de una página que no puede desplazarse más queda mostrando **0** de forma permanente mientras el texto accesible dice **7** (arriba, otro número visible muestra 20 correctamente). Todo número que no llega a ser visible ≥ 50 % dentro de esos márgenes (pantalla corta, último bloque de la página, pestaña en segundo plano) se ve como un cero que parece real. Sugerencia: pintar el valor final por defecto y animar sólo cuando el observador dispare (o completar el valor al salir de `output`).
